# pnm-decode user guide

`pnm-decode` reads one local DOCSIS PNM capture, identifies its binary format
and writes human-readable JSON. It works offline and does not need the desktop UI.
The toolkit is under development.

## Build or install

See [CLI source builds](../install/source.md) and
[installation and binary availability](../install/README.md). With the
repository-local development toolchain already installed, build only the CLI:

```bash
./scripts/cargo-local.sh build --release --locked -p pnm-decode
./target/release/pnm-decode --help
```

The examples below use `pnm-decode` on PATH. From a source checkout, substitute
`./target/release/pnm-decode` on Linux/macOS or
`.\target\release\pnm-decode.exe` in Windows PowerShell.

## Decode a capture

```bash
pnm-decode capture.bin
pnm-decode capture.bin --output result.json
pnm-decode "captures/modulation profile.bin" --stdout
pnm-decode capture.bin --header-only
```

The filename extension does not select a parser: the file's signature and
version do. Default output replaces the input extension with `.json`.
`--output` chooses a different path; its parent directory must already exist.
Existing files and symlinks are never replaced, including the input itself.
Use a new destination or `--stdout` to inspect JSON without creating a file.

`--header-only` exports common metadata without interpreting the measurement
payload. Use it for symbol captures, whose payload decoder is a stub.

| Option | Behavior |
| --- | --- |
| `-o PATH`, `--output PATH` | Choose a new destination JSON file |
| `--stdout` | Write JSON to stdout; cannot combine with `--output` |
| `--header-only` | Export common header metadata only |
| `-h`, `--help` | Show command help |
| `-V`, `--version` | Show the executable version |
| `--` | End options, for example `pnm-decode -- -capture.bin` |

The CLI supports more measurement families than the current
[Qt viewer](../ui/measurements.md). Enabled file-format version is **1.0**;
see [format contracts and evidence](../reference/formats.md).

JSON uses `null` for unavailable measurements and preserves complex samples as
`iq` pairs ordered `[in-phase, quadrature]`. Fields with unit suffixes, such as
`frequency_hz` or `theoretical_throughput_bps`, carry those units;
check the format contract for legacy field names. Latency counters are exact
64-bit integers: readers must preserve them rather than round through a
JavaScript Number.

### Modulation-profile output

```bash
pnm-decode modulation_profile.bin --output modulation_profile.json
```

Every profile retains its compressed schemes. Assignments include textual
`modulation_order` (for example `qam_4096`), the original
`modulation_order_code`, `bit_loading` and `carrier_type`. Skip schemes use the
corresponding `main_` and `skip_` fields.


Modulation-profile JSON keeps OSSI carrier roles and original assignment codes.
It also exports the PHY `constellation`, `bit_loading` and
`shannon_minimum_mer_db`: PLC data is 16-QAM (4 bits, approximately 11.76 dB
ideal bound); continuous pilots are BPSK (1 bit, 0 dB ideal bound). PLC's BPSK
preamble has its own `preamble` object. Skip schemes use `main_` / `skip_` prefixes.
These calculated bounds are not measured MER or receiver thresholds. PLC and
pilots remain excluded from `bandwidth_bps`. No extra CLI option is needed.
See the [field contract](../reference/formats.md#modulation-profile-json-assignments)
and [complete example](examples/modulation-profile.json).


Each `profiles[]` entry has `bandwidth_bps` directly beside its ID and schemes:

```json
{
  "profile_id": 3,
  "bandwidth_bps": 2222400000
}
```

This is the data-carrier-only ideal gross bit rate. It appears automatically in
normal file output (`--output` or the default destination) and `--stdout`; no
extra flag is required. The shared Rust helper calculates it once, and it equals
`analysis.theoretical_throughput_bps`. Every profile also contains `analysis`:

```json
{
  "data_subcarrier_count": 7408,
  "data_bits_per_symbol": 88896,
  "data_bandwidth_hz": 185200000,
  "theoretical_throughput_bps": 2222400000
}
```

This excerpt is profile 3 of the linked example. The complete analysis also
records its basis, useful-symbol duration, excluded overheads and completeness.
The ideal gross rate excludes cyclic-prefix, FEC and other PHY/MAC overhead;
it is not measured application throughput. Reserved/unknown assignments make
that rate unavailable (`null`). See the
[capacity calculation contract](../reference/formats.md#per-profile-ideal-capacity-analysis).
The CLI and desktop export the same core representation. Desktop profile,
metric and carrier visibility selections do not remove profiles from JSON.

### Constellation Display output

`const_display.bin` is detected automatically. Its normal JSON output includes
all measured `iq` pairs unchanged and `constellation_analysis.reference` with
the normalized hard-reference QAM points, bit loading, scaling multiplier and
nearest-reference `decision_boundaries`. Soft samples are not rescaled. Unknown
modulation retains the samples and exports a null reference. No extra CLI flag
is needed. See the [complete JSON example](examples/constellation.json) and
[reference contract](../reference/formats.md#constellation-display-reference-analysis).

### Upstream pre-equalization output

```bash
./target/release/pnm-decode tests/fixtures/pypnm/tests/files/us_pre_equalizer_coef.bin --stdout
```

Current PNN6 and last-update PNN7 exports include `pre_equalization_analysis`:
full-resolution
`frequencies_hz`, `magnitude_db`, and `group_delay` pairs with `frequency_hz` and
`delay_s` in seconds. This is the coefficient correction response, not measured
plant delay. Raw I/Q and header metadata remain unchanged. Undefined magnitudes
and delays are null. No additional CLI option is needed. Last-update files keep
their s1.14 I/Q output; current files keep s2.13. The variants are analyzed
independently. Decode a last update with:

```bash
./target/release/pnm-decode tests/fixtures/pypnm/tests/files/us_pre_equalizer_coef_last.bin --stdout
```

See the [field contract](../reference/formats.md#upstream-pre-equalization-analysis)
and the complete [current](examples/upstream-pre-eq.json) and
[last-update](examples/upstream-pre-eq-last.json) examples.

## Limits and errors

Input and serialized JSON are limited to **16 MiB each**, excluding the final
output newline. Decode policy allows **65,536 items**. These are application
limits, not protocol limits. Diagnostics go to stderr and retain parser field
and byte-offset information; stdout contains JSON only when requested.

| Exit code | Meaning |
| --- | --- |
| 0 | Success, help or version |
| 1 | File/stream I/O failure or existing destination |
| 2 | Invalid command usage |
| 3 | Unsupported identity, version, layout or decoder |
| 4 | Invalid capture or resource/output limit |

File output is fully generated before publication, which requires filesystem
hard-link support. If that fails, use `--stdout` or another filesystem. Normal
errors clean up temporary siblings; forced termination can leave
`.pnm-decode-*.tmp` files. Shell redirection such as `> result.json` follows the
shell's overwrite rules; the CLI's no-replacement protection applies to its
own default/`--output` destinations.

See the [man page](../../crates/cli/man/pnm-decode.1), installed as
`pnm-decode(1)`. Windows users can use `pnm-decode.exe --help` and this guide.
Local validation has been performed on Ubuntu 22.04 x86_64; consult the native
CI results for Windows/macOS validation.

## RxMER bit-loading analysis

Use the same Rust calculation as the desktop popup without launching Qt:

```bash
pnm-decode rxmer.bin --rxmer-bit-loading \
  --start-hz 650000000 --stop-hz 675000000 \
  --model webui_mer_heuristic --margin-db 0 --max-bit-loading 13 \
  --output rxmer-analysis.json
```

Without both Hz bounds, the analysis covers the full capture. Bounds are inclusive
carrier-center limits and must lie inside it. Omit both or provide both. Use
`--stdout` instead of a file; default analysis output is `INPUT.bit-loading.json`.
Existing destinations are never overwritten. Analysis requires an RxMER file
and cannot be combined with `--header-only`.

| Option | Accepted values |
| --- | --- |
| `--rxmer-bit-loading` | Enable analysis output instead of raw decoded fields |
| `--model` | `webui_mer_heuristic` (default), `ossi_candidate_defaults`, `ideal_shannon` |
| `--margin-db` | Finite nonnegative additional MER margin; default 0 |
| `--max-bit-loading` | Known data assignment: 2, 4, 6–14 bits; default 13 (8192-QAM cap) |
| `--start-hz`, `--stop-hz` | Ordered inclusive integer Hz bounds inside the capture |

The [complete analysis example](examples/rxmer-bit-loading.json) uses the bundled
fixture's 650–675 MHz range: 1,001 measured carriers, minimum 39.25 dB, uniform
1024-QAM and **250,250,000 gross bit/s** under the default WebUI model.
The [RxMER guide](../ui/measurements/rxmer/README.md#modulation--capacity)
explains the graph, policies, missing-carrier handling and throughput assumptions.

Gross rate is measured carrier count × uniform bits/symbol × spacing. It assumes
those positions carry data and excludes LDPC/FEC, cyclic-prefix, pilot/PLC and
MAC overhead. Carrier roles and device modulation capability are not inferred
from RxMER. A policy estimate is not an error-free guarantee. Scenario rates are
hypothetical even when their status is `below_target` or `not_covered_by_model`.

The viewer’s **Modulation & Capacity** popup starts with OSSI candidate
defaults. Use `--model ossi_candidate_defaults` to reproduce that initial
selection in the CLI; the CLI’s existing WebUI heuristic default is unchanged.

## Pre-EQ precheck and correction comparison

Use a current PNN6 baseline and a last-update PNN7 correction. Validate the
pair without predicting a result:

```bash
pnm-decode original.bin --pre-eq-update update.bin --precheck-only --stdout
```

The precheck requires matching supported versions, channel, CM MAC, CMTS MAC,
frequency grid, payload length and coefficient count. The correction timestamp
must be strictly newer; filenames and filesystem times do not override it.
Invalid pairs exit4 without writing output. Precheck JSON includes the two
headers, matching grid/device fields and positive encoded file-time gap.

Calculate with an explicit mode; there is no automatic mode selection:

```bash
pnm-decode original.bin --pre-eq-update update.bin --update-mode adjust --output comparison.json
pnm-decode original.bin --pre-eq-update update.bin --update-mode set --stdout
```

Adjust multiplies decoded complex coefficients; Set replaces them. The output
contains predicted coefficients and their difference from the original, raw and
level-aligned dB changes, full-channel spans, group-delay changes in seconds,
precheck metadata and limitations. This is the same Rust analysis as the viewer.
The separate Q formats (current s2.13, last update s1.14) are decoded before math.
There is no simulated clipping, rounding, rejection or modem normalization.

Without `--output` or `--stdout`, default outputs are `original.precheck.json`
or `original.pre-eq-comparison.json`. Existing destinations are never replaced.
Pairing options cannot be combined with RxMER analysis or `--header-only`.
`--precheck-only` excludes `--update-mode`; missing/unknown modes are usage errors.
A later file time does not prove update adjacency or actual application status.

See the [current Pre-EQ guide](../ui/measurements/upstream-pre-eq/README.md#correction--delta-from-the-left-gutter)
and [full synthetic comparison example](examples/pre-eq-comparison-synthetic.json).
